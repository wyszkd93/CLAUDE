# 크리스마스 트리 — HTML 캔버스 버전

브라우저에서 돌아가는 회전 크리스마스 트리입니다. 글자 8,500개로 나무를 만들고, 줄기에서 바깥으로 자란 뒤 황금 전구 줄·장식 공·반짝이는 전구·빛나는 별이 붙습니다. **`index.html` 파일 하나**가 전부이고 외부 라이브러리와 네트워크가 필요 없습니다(더블클릭해서 열면 됩니다).

## 열기

`index.html`을 브라우저로 열면 됩니다. 공유하려면 이 파일 하나만 보내거나 아무 정적 호스팅(GitHub Pages 등)에 올리세요.

| 조작 | 동작 |
|---|---|
| `Space` | 일시정지 / 재생 |
| `R` | 처음부터(다시 자라는 모습) |
| `H` | HUD(시간·회전각·글자 수) 켜기/끄기 |
| `F` | 전체 화면 |
| 오른쪽 아래 ⚙ | 글자, 글자 수, 전구 수, 회전 속도, 그리기 품질 바꾸기 |

주소 뒤에 인자를 붙여 같은 나무를 공유할 수 있습니다.

```
index.html?text=HAPPY%20NEW%20YEAR&letters=12000&lights=250&spin=25&seed=3
```

| 인자 | 기본 | 설명 |
|---|---|---|
| `text` | MERRY CHRISTMAS | 나무에 쓸 글자(최대 40자) |
| `letters` | 8500 | 글자 수. 가지마다 글자가 하나는 있어야 해서 하한(97)이 있고 더 작은 값은 하한으로 올립니다 |
| `lights` | 170 | 전구 수 |
| `spin` | 15 | 초당 회전 각도(도, 음수는 반대 방향) |
| `seed` | 7 | 같은 값이면 항상 같은 나무 |
| `quality` | auto | `auto`는 느리면 스스로 낮춥니다. `0`(최고)~`4`(최저)는 고정 단계입니다 |
| `paused` | | 값과 상관없이 있으면 정지 상태로 열고 첫 장면만 그립니다 |

## 만드는 방식

1. **가지**: 층(9개)마다 가지를 방사형으로 뻗습니다. 아래층일수록 가지가 많고, 층마다 각도를 황금비(0.618)만큼 어긋나게 돌립니다.
2. **글자**: 가지마다 점을 뿌립니다. 끝쪽에 더 몰리고, 끝으로 갈수록 처지며, 옆으로 퍼집니다. 점 하나가 글자 하나입니다.
3. **자라기**: 줄기에서 가깝고 꼭대기에 가까운 글자부터 10초 동안 늘어납니다(453개에서 시작).
4. **명암**: 가까울수록 밝고, 줄기 쪽은 어둡고 가지 끝은 밝습니다. 군데군데 반짝이는 잎이 있습니다.
5. **장식**: 다 자라면 황금 줄이 위에서부터 감기고, 장식 공이 나타나고, 전구가 하나씩 켜지고, 별이 빛납니다.
6. **그리기**: y축 회전 → 원근 투영 → 깊이 정렬 → 스프라이트 찍기.

## 빠르게 돌아가는 이유 (성능)

처음 버전은 느렸습니다(1400×900에서 DPR 1 약 42ms, 고해상도 DPR 2 약 99ms). 구간별로 기능을 하나씩 꺼 보며 측정해서 병목을 찾았고, 병목 순서대로 고쳤습니다.

| 병목 | 고친 방법 |
|---|---|
| 글자·장식 스프라이트 약 9,500번을 찍는 비용(DPR 1에서 84%). 스프라이트가 360개의 별도 캔버스라 호출마다 원본이 바뀌고, 40px 원본을 10~20px로 줄여 찍어 리샘플링도 발생 | 모든 스프라이트를 **한 장의 아틀라스**에 미리 그려 둡니다. 화면에서 실제 쓰는 크기를 최대 8단계로 나눠 각각 만들어 두고 **확대·축소 없이 정수 좌표로 그대로** 찍습니다 |
| 다른 글자에 완전히 가려진 안쪽 글자까지 그림(평균 11겹) | **가려짐 컬링**: 가까운 것부터 보며 화면 칸마다 몇 겹이 찼는지 세어, 충분히 찬 칸의 글자는 건너뜁니다. 겹침 허용 수는 측정으로 정했습니다(허용 3은 덮인 면적 -1.1%로 모습이 거의 같고 약 38% 빠릅니다. 장식·전구·줄은 절대 건너뛰지 않습니다) |
| 고해상도에서 배경 전체 복사와 바닥 빛의 전체 화면 가산 혼합(DPR 2에서 합쳐 약 29%) | 배경은 **별도 정적 캔버스**, 바닥 빛은 **CSS 투명도**로 분리해 프레임마다 다시 칠하지 않습니다 |
| 120/144Hz 화면에서 필요 이상으로 그림 | **60fps 상한** |
| 별·눈을 하나씩 칠하고, 정렬 버퍼를 매 프레임 새로 만듦 | 밝기·크기 단계별로 묶어 한 번에 칠하고, 버퍼를 재사용합니다 |

측정값(이 환경의 헤드리스 Chromium, 1400×900, 글자 8,500개, 여러 번 돌린 범위): DPR 1 약 42ms → **13~17ms**, DPR 2 약 99ms → **17~25ms**. 측정마다 흔들려서 단일 값 대신 범위로 적습니다.

### 적응형 품질

그래도 느린 기기를 위해 프레임이 계속 느리면 **스스로 품질을 낮춥니다**(`quality=auto`, 기본).

| 단계 | 해상도 배율 | 그리는 글자 | 번짐 | 컬링 허용 |
|---|---|---|---|---|
| 0 최고 | 최대 2 | 100% | 있음 | 3 |
| 1 높음 | 최대 1.5 | 100% | 있음 | 3 |
| 2 보통 | 1 | 75% | 있음 | 2 |
| 3 낮음 | 1 | 55% | 없음 | 1 |
| 4 최저 | 0.75 | 40% | 없음 | 1 |

- 약 45fps 미만이 계속되면 한 단계, 약 25fps 미만이면 더 빨리 두 단계씩 내립니다. 55fps 이상이 6초 넘게 이어지면(최대 2번) 한 단계 올립니다.
- 탭 전환 같은 1초 넘는 정지는 무시하고, 짧게 튀는 프레임은 잘라서 반영해 한두 번 튀는 값으로 품질을 잘못 낮추지 않습니다.
- 낮은 품질은 화면이 눈에 띄게 성겨집니다. 가장 좋은 모습은 기기가 감당할 때만 유지됩니다.
- HUD의 `running · NN fps · q2`처럼 `q`가 붙으면 자동으로 낮춘 것입니다. ⚙의 품질 선택이나 `?quality=0`~`4`로 고정할 수 있습니다.

## 테스트

브라우저(Chromium)를 실제로 띄워 검사합니다. [Playwright](https://playwright.dev)가 필요합니다(이 프로젝트의 의존성으로 선언하지는 않았습니다).

```bash
cd web
npm test        # 문법 검사 → 브라우저 테스트 53개
```

- 난수·글자 수 배분·가지 모양·성장·전구/줄/장식 시점·투영·깊이 정렬·눈·HUD·URL 인자·컨트롤·창 크기 변경 같은 로직
- 성능 구조: 모든 스프라이트를 **단일 아틀라스에서 크기 변환 없이 정수 좌표로** 찍는지, 컬링이 장식을 건드리지 않는지, 60fps 상한, 품질 단계, 적응형 품질(느린 기기를 흉내 내는 `simCostMs` 훅으로 기기 속도와 무관하게 검사), 성능 기준선
- 화면 검사: 픽셀을 읽어 초록(나무), 황금(줄), 빨강(공), 별 빛이 자라는 시점에 맞게 나타나는지, 같은 시각은 항상 같은 그림인지
- 문법 오류가 있으면 브라우저 테스트가 타임아웃으로 줄줄이 실패해 원인이 가려지므로, 먼저 인라인 스크립트 문법만 따로 검사합니다(`scripts/check-syntax.mjs`).
- 다른 파일을 검사하려면 `XMAS_HTML=/경로/index.html npm test`

## 한계

- **성능은 GPU 있는 실제 브라우저에서 재 보지 못했습니다.** 위 수치는 이 환경의 헤드리스 Chromium(소프트웨어 렌더링)에서 잰 상대 개선율입니다. 느린 기기는 적응형 품질이 스스로 낮추지만, 실제 체감 프레임은 기기마다 다릅니다.
- HiDPI는 최대 2배까지만 키웁니다.
- Safari, Firefox 등 Chromium이 아닌 브라우저에서는 확인하지 않았습니다.
- 영상 원본의 정확한 색감·가지 모양·장식 위치는 스크린샷으로 짐작한 값입니다.
